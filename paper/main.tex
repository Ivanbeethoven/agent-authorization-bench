\begin{abstract}
An agent can invoke a tool with a permitted name while exceeding the user's authority over its effects. We let the tool preview every affected object, destination and quantity, verify those effects against a user-confirmed grant in code, and ask a decision model to assess remaining qualitative conditions. We compare four policies on \EffectTotalCases{} previously unused requests in document sharing, inventory transfer and payment refunds. The verifier with Jev released \EffectJointLegal{} of \EffectLegalDenom{} authorized requests and made \EffectJointFalse{} false releases in \EffectHoldDenom{} non-execution cases. Direct DeepSeek released \EffectDirectLegal{} authorized requests and made \EffectDirectFalse{} false releases. The equal-benchmark, equal-class probability of a correct decision rose from \EffectDirectScore{} to \EffectJointScore{}. Removing the verifier caused 27 additional false releases without changing legal access. Substituting DeepSeek for Jev preserved all legal releases and stopped both residual errors, at 3.55 times the estimated API cost of using Jev. These results isolate an advantage from checking typed effects and quantify the residual trade-off between the two qualitative reviewers.
\end{abstract}

\section{Introduction}
Authorization applies to what a tool call will change. A recipient group can expand to outsiders, a stock transfer can exceed its limit across several lines, and repeated entries can turn a permitted adjustment into an excessive refund. In each case a model must infer effects from the proposal before it can compare them to authority. Tools already hold the mappings and types needed to make many of these effects explicit.

We study an interface that has two sources of authority and state. The user confirms a grant such as the objects and destinations a transaction may affect. The tool previews the proposed effects from its own parameters and catalog. A host verifier checks quantitative and categorical restrictions. A model interprets only the remaining procedural condition, such as whether a current approval covers the production operation. This division produces three testable questions. Does the complete method preserve more legal access at the same or lower false-release count than a direct model? Which errors recur if we remove the program? What changes when the same qualitative cases go to a different reviewer?

Access-control principles require that a host mediate every action and default to withholding when the requisite authority has not been established \cite{saltzer}. CaMeL tracks capabilities and separates control from untrusted data in tool-using agents \cite{camel}. Our focus is narrower: verifying the concrete effects of a single proposal against a confirmed grant and localizing the gains with paired comparisons. AuthGateBench varies user scope while holding the proposed action and history fixed \cite{authgate}. DelegationBench distinguishes authorization requests, missing information and conditions for refusal \cite{delegation}. SteerBench-Work studies whether a workplace action should proceed or wait \cite{steerwork}. We adopt counterfactual scope and condition changes to isolate the effects of a verifiable tool representation.

\section{Method}
\paragraph{Grant and preview.}
A user confirms a grant \(g=(o,u,O,D,\ell,L,c)\), where \(o\) is a tool operation, \(u\) its unit, \(O\) the permitted objects, \(D\) the permitted destinations, \(\ell\) a per-object upper bound, \(L\) a transaction upper bound, and \(c\) an optional qualitative condition. The confirmed form is the source for the structured grant. This setting requires that the user see and approve the actual fields.

Before any side effect, tool code previews a finite list \(E\) of rows \((x,d,q)\) for the exact proposal, with object \(x\), destination \(d\), and a positive integer quantity \(q\) in the declared unit. The sharing tool resolves an audience to explicit principals and emits one row for each link it would issue. The transfer tool emits one row per stock line in units. The refund tool resolves the destination and reports each adjustment in cents. A preview says what the tool will do. It does not grant permission.

\paragraph{Programmatic and qualitative decisions.}
The host checks the operation and unit, verifies that \(E\) is nonempty, checks \(x\in O\) and \(d\in D\) for every row, verifies valid quantities, and checks
\[
     \sum_{(x',\,d,\,q)\in E\,:\,x'=x} q \leq \ell(x)\quad \forall x\in O,
     \qquad
     \sum_{(x,\,d,\,q)\in E} q\leq L.
\]
The sums include repeated rows. A failed check withholds execution. A proposal that passes every check can proceed immediately when \(c\) is absent. Otherwise, a model answers two fixed-choice questions about scope coverage and satisfaction of \(c\), using the original request, confirmed grant, tool preview, parameters and current records. The host releases the proposal only when both answers are affirmative. A context entry about a prior or different operation does not establish clearance for the current one.

\paragraph{Safety property and deployment requirements.}
Assume the preview enumerates every material effect faithfully and the host binds the decision to the same parameters, grant, catalog state and approval snapshot at execution. Every released action then respects the structured bounds because all releases pass the preceding predicates. The property covers the operations and fields represented in the preview. The reviewer still decides whether the qualitative record satisfies \(c\). In a live tool integration, changes to the proposal, roster or approval state between preview and execution require recomputation or an atomic check. This study measures the authorization decision in a local simulation.

\section{Evaluation}
\paragraph{Cases.}
Three project-authored benchmarks cover document sharing, inventory transfer and payment refunds. Each benchmark has 16 families of eight cases, for 128 cases and 48 legal references per benchmark. Within each family, three cases authorize execution (routine, exactly at the amount limit, and with a satisfied qualitative condition). Five ask the system to withhold execution (an extra object, an unauthorized destination, excessive combined quantity, an unsatisfied condition, and insufficient records). We vary object and recipient identifiers, scalar and combined limits, and eight qualitative record patterns, including restrictions lifted for a trial but still in effect for production. The scenario transformations determine the reference labels. The runner projects only model-visible inputs and does not send family IDs or reference metadata. The artifact provides the input generator and fixed presets. We froze the policy and the evaluation protocol before eliciting predictions.

\paragraph{Matched comparisons.}
All four policies see the same state and tool preview. Direct DeepSeek predicts execute or withhold in a single call. Jev only uses the two review questions in all cases. Verifier plus Jev applies the program and consults Jev on the cases with passing structured checks and a qualitative condition. Verifier plus DeepSeek uses the same program, review cases and questions as the Jev version. The Jev call on a reviewed request is shared between the Jev-only and verifier-plus-Jev policies, so their comparison changes only the program's effect on the decision. We use \texttt{deepseek-flash} in non-thinking JSON mode at temperature zero and \texttt{jev-1.14.0} with fixed-choice outputs \cite{dsapi,jevapi}.

\paragraph{Endpoints.}
For benchmark \(b\), let \(L_b\) count legal requests, \(N_b\) count requests that should be withheld, \(A_b\) count correctly released legal requests, and \(F_b\) count false releases. We report accuracy, both error directions, and the normalized probability
\[
    S=\frac{1}{B}\sum_{b=1}^{B} S_b,
    \qquad S_b=\frac12\left(\frac{A_b}{L_b}+1-\frac{F_b}{N_b}\right).
\]
This is the empirical chance of a correct decision under uniform sampling over benchmarks, then over the two reference classes, then over observations in that class. It is a benchmark-level performance measure. A method that always withholds scores 0.5. We prespecified higher legal-release counts with no increase in false-release counts in any benchmark relative to direct DeepSeek. We also count newly introduced and prevented false releases separately. We estimate percentile intervals for paired score changes using 5,000 family-level resamples, independently within each benchmark. Each draw keeps every variant and policy for a sampled family together.

Time is the sum of serial API time required for each decision, including any retries. Locally decided requests contribute zero API time. Usage-based fees use recorded input and output tokens, cache status and the provider time band where applicable. We report fees per policy and count shared calls once when reporting the cost of running the experiment.

\paragraph{What the verifier contributed.}
Removing the program caused 27 additional false releases at the same 144 legal releases. The verifier stopped 26 excessive-total proposals and one unauthorized object that Jev alone would release. The 96 unconditional legal cases passed in code and 144 structured violations stopped in code. The remaining 144 cases went to review. The API call rate thus fell from one per case to 0.375. Mean API latency fell from 2.348 to \EffectJointTime{} seconds relative to Jev only. Local verification took a mean of \EffectLocalTime{} microseconds on the evaluation host.

\paragraph{What the reviewer contributed.}
Both reviewers released all 48 conditionally authorized actions. Jev also released two inventory transfers where a trial restriction had ended and the production restriction was still active. DeepSeek stopped both with the same inputs and questions. Verifier plus DeepSeek therefore reached 1.0000 on this population, with zero false releases and 144 legal releases. Its mean API latency was 0.282 seconds, compared with \EffectJointTime{} seconds for Jev, while its estimated fee was CNY 0.1173, compared with CNY \EffectJointFee{} for Jev. Across the four policies, the experiment used \EffectStudyCalls{} distinct API calls at an estimated CNY \EffectStudyCost{}.

\section{Discussion}
The program's observed benefit is concentrated in conditions it can decide exactly. In particular, it adds quantities before comparing them with the grant. A reviewer still has to bind qualitative clearance to the correct environment and current operation. The residual Jev errors share this mechanism. They show why counting only final errors can hide a newly introduced release after the underlying system has become more selective.

The three benchmarks have explicit user-confirmed grants, faithful simulated previews and English records generated from a finite set of scenario transformations. The reference labels specify intended execution behavior by construction. This setup isolates the effect of the verifier and makes the two substitutions comparable. It leaves open the rates on free-form requests, third-party integrations, and authored records with disputed interpretations. The family intervals describe sensitivity to the observed scenario mix. They do not estimate deployment-wide error rates or variability across model calls. The 384 observed outcomes establish the operating points for these models and this protocol.

\section{Conclusion}
Tool-generated effects made categorical checks and quantity limits mechanically verifiable. On three controlled benchmarks, the verifier with Jev increased legal releases and reduced false releases compared with direct DeepSeek. The matched removal experiment attributed 27 prevented false releases to the program. The matched replacement experiment found fewer false releases and lower latency with DeepSeek, and lower API cost with Jev. Operational use requires a trustworthy preview and an execution boundary that preserves the reviewed state.
