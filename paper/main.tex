\begin{abstract}
Tool authorization depends on which objects an action affects, where its effects occur, and how much it changes. We evaluate a policy-as-code verifier that checks these effects against a user-confirmed grant and refers outstanding qualitative conditions to a model. Across \EffectTotalCases{} fresh cases in three controlled benchmarks, the verifier with Jev released \EffectJointLegal{}/\EffectLegalDenom{} authorized requests and made \EffectJointFalse{}/\EffectHoldDenom{} false releases. Direct DeepSeek released \EffectDirectLegal{}/\EffectLegalDenom{} authorized requests and made \EffectDirectFalse{}/\EffectHoldDenom{} false releases. Removing the verifier while keeping Jev added 27 false releases at the same legal-release count. Substituting DeepSeek as the reviewer stopped both remaining false releases and preserved all legal releases, at 3.55 times the estimated API cost of the Jev configuration. The effect checks prevented numerical and categorical scope violations. The remaining errors concerned which approval applied to the proposed action.
\end{abstract}

\section{Introduction}
An agent can select the right tool and still exceed the user's authorization. A sharing tool can resolve a group to recipients outside the approved audience, and a stock transfer can exceed its limit only when several lines are added together. Both failures arise at the level of effects. Tool implementations already hold the catalogs and quantity types needed to preview those effects before execution.

We study whether a tool-supplied preview lets a host enforce a confirmed grant while preserving access to authorized actions. Our design pairs a deterministic verifier with model review for any remaining condition. Two matched comparisons isolate the verifier's contribution and the effect of changing the reviewer. The direct-model comparison measures the operating point of the complete method.

Complete mediation and fail-safe defaults place the authorization decision at the execution boundary \cite{saltzer}. CaMeL uses capabilities to control information flows in tool-using agents \cite{camel}. We focus on verifying the concrete effects of a single proposal against a confirmed grant. AuthGateBench varies user scope for a fixed action and history \cite{authgate}. DelegationBench distinguishes gaps in authority and information from reasons to refuse \cite{delegation}. SteerBench-Work studies whether to commit or hold workplace actions \cite{steerwork}. Our controlled benchmarks vary previewed effects or approval records within families of actions.

\section{Method}
\paragraph{User grant and tool preview.}
The user sees and confirms the structured grant \(g=(o,u,O,D,\ell,L,c)\). It specifies the operation \(o\), unit \(u\), permitted objects \(O\), permitted destinations \(D\), per-object limits \(\ell\), transaction limit \(L\), and optional qualitative condition \(c\). The confirmed form supplies the authority for the decision.

Before execution, the tool produces a list \(E\) of planned effect rows \((x,d,q)\), with object \(x\), destination \(d\), and positive integer quantity \(q\) in the declared unit. Sharing resolves an audience to recipients and emits one row per new link. Inventory transfer emits one row per stock line. Refunds resolve the payment destination and report each adjustment in cents. The preview describes the proposal's effects (Fig.~\ref{fig:workflow}).

\caption{\textbf{Authorization from tool effects.} The host applies the user-confirmed grant to the tool's preview. A failed check stops execution. Passing proposals proceed directly when no qualitative condition remains. On a conditional proposal, the model must affirm both scope coverage and the applicable condition.}
\label{fig:workflow}
\end{figure}

\paragraph{Policy as code.}
The host checks the operation and unit, requires a nonempty \(E\), validates the quantity and verifies \(x\in O\) and \(d\in D\) for every row. It enforces both quantity limits,
\[
     \sum_{(x',\,d,\,q)\in E\,:\,x'=x} q \leq \ell(x)\quad \forall x\in O,
     \qquad
     \sum_{(x,\,d,\,q)\in E} q\leq L.
\]
Each occurrence counts in the sums. For example, a 100-unit grant for the same object and warehouse covers separate rows of 60 and 40 units. Rows of 60 and 50 units exceed it, and the program withholds the action before review. Passing proposals can execute directly if \(c\) is absent. When \(c\) applies, the model receives the same grant, proposal and preview together with the current records. Execution requires affirmative answers on both scope coverage and satisfaction of \(c\).

\paragraph{Safety property and deployment requirements.}
Every release satisfies the structured bounds when the preview enumerates each effect faithfully and the host executes against the reviewed proposal, grant and state. This property applies to the fields represented in the preview. The qualitative decision depends on the reviewer's assessment of \(c\). A deployment must recheck or atomically bind the proposal, catalog and approvals at execution. We evaluate the decision with local simulated tools.

\section{Evaluation}
\paragraph{Cases.}
Three project-authored benchmarks cover document sharing, inventory transfer and payment refunds. Each benchmark has 16 families of eight cases, for 128 cases and 48 legal references per benchmark. Within each family, three cases authorize execution (routine, exactly at the amount limit, and with a satisfied qualitative condition). Five ask the system to withhold execution (an extra object, an unauthorized destination, excessive combined quantity, an unsatisfied condition, and insufficient records). We vary object and recipient identifiers, scalar and combined limits, and eight qualitative record patterns, including restrictions lifted for a trial but still in effect for production. The scenario transformations determine the reference labels. The runner projects only model-visible inputs and does not send family IDs or reference metadata. The artifact provides the input generator and fixed presets. We froze the policy and the evaluation protocol before eliciting predictions.

\paragraph{Matched comparisons.}
All four policies see the same state and tool preview. Direct DeepSeek predicts execute or withhold in a single call. Jev only uses the two review questions in all cases. Verifier plus Jev applies the program and consults Jev on the cases with passing structured checks and a qualitative condition. Verifier plus DeepSeek uses the same program, review cases and questions as the Jev version. The Jev call on a reviewed request is shared between the Jev-only and verifier-plus-Jev policies, so their comparison changes only the program's effect on the decision. We use \texttt{deepseek-flash} in non-thinking JSON mode at temperature zero and \texttt{jev-1.14.0} with fixed-choice outputs \cite{dsapi,jevapi}.

\paragraph{Endpoints.}
For benchmark \(b\), let \(L_b\) count legal requests, \(N_b\) count requests that should be withheld, \(A_b\) count correctly released legal requests, and \(F_b\) count false releases. We report accuracy, both error directions, and the normalized probability
\[
    S=\frac{1}{B}\sum_{b=1}^{B} S_b,
    \qquad S_b=\frac12\left(\frac{A_b}{L_b}+1-\frac{F_b}{N_b}\right).
\]
This is the empirical chance of a correct decision under uniform sampling over benchmarks, then over the two reference classes, then over observations in that class. It is a benchmark-level performance measure. A method that always withholds scores 0.5. We prespecified higher legal-release counts with no increase in false-release counts in any benchmark relative to direct DeepSeek. We also count newly introduced and prevented false releases separately. We estimate percentile intervals for paired score changes using 5,000 family-level resamples, independently within each benchmark. Each draw keeps every variant and policy for a sampled family together.

Time is the sum of serial API time required for each decision, including any retries. Locally decided requests contribute zero API time. Usage-based fees use recorded input and output tokens, cache status and the provider time band where applicable. We report fees per policy and count shared calls once when reporting the cost of running the experiment.

\section{Results}

\paragraph{Legal access and false releases.}
Verifier plus Jev gained \EffectLegalGain{} legal releases and lost none relative to direct DeepSeek (Fig.~\ref{fig:outcomes}). It prevented \EffectPreventedFalse{} false releases and introduced \EffectNewFalse{} (Table~\ref{tab:paired}). False-release counts fell or stayed constant within each benchmark. The equal-weight score increased from \EffectDirectScore{} to \EffectJointScore{}, a difference of 15.07 percentage points (95\% paired family-resampling interval 12.64 to 17.71).

\paragraph{Contribution of the program.}
Compared with Jev alone, the verifier intercepted 26 excessive-quantity proposals and one proposed action on an unauthorized object. Both methods released all 144 legal requests. The program directly allowed 96 unconditional requests and withheld 144 structured violations. This left 144 proposals for review, reducing the number of Jev calls by 62.5\%. Mean API latency fell from 2.348 to \EffectJointTime{} seconds per request. Local verification took \EffectLocalTime{} microseconds on average.

\paragraph{Contribution of the reviewer.}
Both reviewers released all 48 conditionally authorized actions. Their decisions differed on two inventory transfers. Jev accepted the end of a trial restriction even though the corresponding production restriction remained active. DeepSeek withheld both on the same inputs, giving zero observed false releases for the complete policy. The estimated fees were CNY 0.1173 for verifier plus DeepSeek and CNY \EffectJointFee{} for verifier plus Jev. The corresponding mean API times were 0.282 and \EffectJointTime{} seconds. The experiment used \EffectStudyCalls{} distinct API calls at an estimated CNY \EffectStudyCost{}.

\section{Discussion}
The main gain came from representing quantities and object identities in a form the host could evaluate. The two residual errors came from interpreting which environment an approval covered. Even after aggregate false releases fell, those decisions changed from hold to release. Paired reporting makes that change visible.

The benchmark design controls grant structure and preview fidelity, which makes the two component comparisons interpretable. Each domain uses a finite set of authored variants, with execution labels determined by construction. The resulting rates describe structured grants and simulated tools. Live integrations add uncertainty about whether the preview fully captures the actual effects, and free-form grants add uncertainty about the authority encoded in the form. The family intervals describe sensitivity to the observed scenario mix. Each policy was evaluated once per request.

\section{Conclusion}
Tool effect previews let a host verify categorical restrictions and quantity limits before execution. In this evaluation, the verifier preserved legal access and prevented scope violations that escaped a model alone. The choice of reviewer affected conditional mistakes, latency and cost. A deployment must preserve the integrity of the preview and the state it describes.
