\begin{abstract}
A tool can resolve a single agent request into several effects, only some of which the user authorized. We evaluate a host that checks each previewed effect against a confirmed grant and refers outstanding approval conditions to a model. Across 1,824 simulated sharing, transfer and refund requests, adding these checks to the same Jev reviewer prevented 274 false releases and preserved every authorized release made by Jev alone. Approval from the wrong source accounted for 129 of the 130 false releases under verifier plus Jev in the 1,440-case replication. Replacing Jev with DeepSeek reduced false releases to 28, while authorized releases fell from 428 to 375 of 432. We also tested a local reviewer trained on matched office requests. On 1,126 public authorization requests, substituting it for Jev in a pipeline produced 101 more false releases and 49 fewer authorized releases. The controlled benefit came from checking object and quantity limits. Determining whose approval covers a particular action remains an open problem.
\end{abstract}

\section{Introduction}
An agent can select the right tool and still exceed the user's authorization. A sharing tool can resolve a group to recipients outside the approved audience. A stock transfer can cross a limit when its line items are added together. The host can check either condition if the tool previews its concrete effects. A grant that also requires approval from a warehouse manager poses a different question. A record can say that the transfer was approved while naming someone who had no authority to approve it. We measure how checking effects and interpreting approval records each contribute to authorized access and to erroneous releases.

Complete mediation places an authorization check on each access \cite{saltzer}. CaMeL uses capabilities to control information flows in tool-using agents \cite{camel}. Progent evaluates symbolic privileges over tool names and arguments \cite{progent}, and AgentSpec specifies runtime interventions through triggers, predicates and enforcement actions \cite{agentspec}. Our unit of checking is the set of effects a tool computes after resolving its arguments. This lets us isolate the contribution of per-object and transaction limits while holding the model's answers fixed.

We first vary effects and approval records within families of simulated actions. A paired comparison with and without the program tests the value of the structural checks. Changing only the reviewer on the same conditional proposals tests how approval interpretation affects the result. We then examine a different setting in which public benchmarks provide instructions, observations and a proposed action in their own formats \cite{authgate,delegation,steerwork}. There we test whether a trained local classifier can replace a hosted reviewer on the same cases selected for review.

\section{Method}
\paragraph{User grant and tool preview.}
The user sees and confirms the structured grant \(g=(o,u,O,D,\ell,L,c)\). It specifies the operation \(o\), unit \(u\), permitted objects \(O\), permitted destinations \(D\), per-object limits \(\ell\), transaction limit \(L\), and optional qualitative condition \(c\). The confirmed form supplies the authority for the decision.

Before execution, the tool produces a list \(E\) of planned effect rows \((x,d,q)\), with object \(x\), destination \(d\), and positive integer quantity \(q\) in the declared unit. Sharing resolves an audience to recipients and emits one row per new link. Inventory transfer emits one row per stock line. Refunds resolve the payment destination and report each adjustment in cents. The preview describes the proposal's effects (Fig.~\ref{fig:workflow}).

\paragraph{Policy as code.}
The host checks the operation and unit, requires a nonempty \(E\), validates the quantity and verifies \(x\in O\) and \(d\in D\) for every row. It enforces both quantity limits,
\[
     \sum_{(x',\,d,\,q)\in E\,:\,x'=x} q \leq \ell(x)\quad \forall x\in O,
     \qquad
     \sum_{(x,\,d,\,q)\in E} q\leq L.
\]
Each occurrence counts in the sums. For example, a 100-unit grant for the same object and warehouse covers separate rows of 60 and 40 units. Rows of 60 and 50 units exceed it, and the program withholds the action before review. Passing proposals can execute directly if \(c\) is absent. When \(c\) applies, the model receives the same grant, proposal and preview together with the current records. Execution requires affirmative answers on both scope coverage and satisfaction of \(c\).

\paragraph{Safety property and deployment requirements.}
The agent proposes the operation and its arguments. The host obtains the grant from the user-confirmed form and the effect list from the tool and its catalog. The agent has no authority to expand the grant. Under this trust model, every route to release passes the same structural checks. A model answer cannot override a failed quantity or destination check. The property covers the effects enumerated by the preview and assumes that the same proposal, grant and catalog state apply at execution. A live integration would need to bind or recheck that state and the applicable approvals. Our experiments end at the release decision, before any external action.

\section{Evaluation}
\paragraph{Cases.}
Three project-authored benchmarks cover document sharing, inventory transfer and payment refunds. Each benchmark has 16 families of eight cases, for 128 cases and 48 legal references per benchmark. Within each family, three cases authorize execution (routine, exactly at the amount limit, and with a satisfied qualitative condition). Five ask the system to withhold execution (an extra object, an unauthorized destination, excessive combined quantity, an unsatisfied condition, and insufficient records). We vary object and recipient identifiers, scalar and combined limits, and eight qualitative record patterns, including restrictions lifted for a trial but still in effect for production. The scenario transformations determine the reference labels. The runner projects only model-visible inputs and does not send family IDs or reference metadata. The artifact provides the input generator and fixed presets. We froze the policy and the evaluation protocol before eliciting predictions.

We then froze an expansion of 48 new ten-case families per benchmark before inference. Its 1,440 requests use family identifiers and request texts absent from the initial cohort. The expansion includes multiple objects, split line items, asymmetric limits and independent violations of per-object and transaction ceilings. It also tests 16 approval patterns, with affirmative records tied to the correct source, effective period and operation. Each family includes three legal cases and seven non-execution cases. We reuse the models, prompts, routing and score definitions. We report the two cohorts separately because their case distributions differ.

\paragraph{Matched comparisons.}
All four policies see the same state and tool preview. Direct DeepSeek predicts execute or withhold in a single call. Jev only uses the two review questions in all cases. Verifier plus Jev applies the program and consults Jev on the cases with passing structured checks and a qualitative condition. Verifier plus DeepSeek uses the same program, review cases and questions as the Jev version. The Jev call on a reviewed request is shared between the Jev-only and verifier-plus-Jev policies, so their comparison changes only the program's effect on the decision. We use \texttt{deepseek-flash} in non-thinking JSON mode at temperature zero and \texttt{jev-1.14.0} with fixed-choice outputs \cite{dsapi,jevapi}.

\paragraph{Endpoints.}
For benchmark \(b\), let \(L_b\) count legal requests, \(N_b\) count requests that should be withheld, \(A_b\) count correctly released legal requests, and \(F_b\) count false releases. We report accuracy, both error directions, and the normalized probability
\[
    S=\frac{1}{B}\sum_{b=1}^{B} S_b,
    \qquad S_b=\frac12\left(\frac{A_b}{L_b}+1-\frac{F_b}{N_b}\right).
\]
Here \(A_b/L_b\) is the authorized-release rate and \(1-F_b/N_b\) is recall for actions that should be withheld. Their mean is balanced accuracy within a benchmark. The score gives each benchmark equal weight. A policy that always withholds scores 0.5. Our safety-first comparison also requires more authorized releases overall and no increase in false-release counts in any benchmark relative to direct DeepSeek. For each non-executable case we distinguish an error introduced by the new policy from one it prevents. A net reduction can include both. We estimate percentile intervals for paired score changes using 5,000 family-level resamples within each benchmark, keeping each sampled family's variants and policies together.

Time is the sum of serial API time required for each decision, including any retries. Locally decided requests contribute zero API time. Usage-based fees use recorded input and output tokens, cache status and the provider time band where applicable. We report fees per policy and count shared calls once when reporting the cost of running the experiment.

\section{Results}
\subsection{Initial cohort}

\paragraph{Legal access and false releases.}
Verifier plus Jev gained \EffectLegalGain{} legal releases and lost none relative to direct DeepSeek. It prevented \EffectPreventedFalse{} false releases and introduced \EffectNewFalse{} (Table~\ref{tab:paired}). False-release counts fell or stayed constant within each benchmark (Table~\ref{tab:rates}). The equal-weight score increased from \EffectDirectScore{} to \EffectJointScore{}, a difference of 15.07 percentage points (95\% paired family-resampling interval 12.64 to 17.71).

\paragraph{Contribution of the program.}
Compared with Jev alone, the verifier intercepted 26 excessive-quantity proposals and one proposed action on an unauthorized object. Both methods released all 144 legal requests. The program directly allowed 96 unconditional requests and withheld 144 structured violations. This left 144 proposals for review, reducing the number of Jev calls by 62.5\%. Mean API latency fell from 2.348 to \EffectJointTime{} seconds per request. Local verification took \EffectLocalTime{} microseconds on average.

\subsection{Reviewer substitution on public authorization requests}
\label{sec:public-review}
The public corpora provide the user's instruction or policy, observations and a proposed tool action in native form. They lack the common confirmed-grant and effect-preview interface of the controlled study. Here DeepSeek extracts authorization facts and a program checks supported fields. On the 813 primary requests selected for model review, we replace Jev with a trained AgentDecision-4B classifier. All other decisions remain fixed. We also compare the original and trained local models acting alone. The 1,126 records come from AuthGateBench (700), DelegationBench (156) and Jev Boundary (270). Each request receives a binary release decision, including those originally labeled as needing information or further authorization. Appendix~\ref{sec:local-classifier} details fitting, calibration and the external cohorts.

\section{Discussion}
The matched comparison holds the reviewer's answers fixed and changes whether the host applies the structural checks. The program prevented releases outside the grant while preserving authorized releases in both controlled cohorts. The choice of reviewer matters once the host has established that the action fits the grant but an approval condition still applies. In the replication, DeepSeek withheld more wrong-source approvals and more genuinely approved requests. The choice between reviewers therefore depends on both costs of error, even when the scope checks are identical.

The public comparison makes the deployment choice concrete. The trained local model improved on its own original decision rule while releasing fewer authorized actions. In the pipeline, Jev retained more authorized releases and made fewer false releases than its local replacement. A useful next experiment would give both reviewers the same authenticated approval record and vary only its signer, scope or revision. A program could check those three fields when the grant identifies them. The paired outcome would show whether that check removes wrong-source releases while preserving valid approvals.

\paragraph{Scope of inference.} The controlled tasks use simulated tools, complete previews and labels determined by authored changes. Their rates describe this mix of cases. An omitted side effect, a stale catalog or an incorrectly recorded grant falls outside the structural property. On the public corpora we measured a repeated evaluation of fixed decisions, including requests that require clarification. A withheld request does not establish that the action would have caused harm. The family intervals quantify sensitivity to case composition. Each policy was evaluated once per request.

\section{Conclusion}
When a tool can enumerate its effects and the user has confirmed the limits, the host can enforce those limits on every release. In both controlled cohorts this preserved authorized access relative to Jev alone. The largest remaining error concerned the authority behind an approval. Reporting false releases alongside authorized access exposed that failure in the hosted system and the cost of substituting a local reviewer.
